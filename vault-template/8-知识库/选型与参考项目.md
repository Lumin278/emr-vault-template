# 选型与参考项目

> 这是**开工前那轮调研的结论页**。
> 用途：以后想"换个方案 / 找现成轮子 / 加新能力"时，从这里起步。
> 星数等为 **2026-09 时点**的快照，仅供参考。

## 一、载体选型：为什么用 Obsidian（而不是自建 App / 向量库）

- **纯 Markdown 文件**：数据是自己的、可读、可迁移；换 Agent、换机器、十年后都能打开。
- **Obsidian 官方 Linux 桌面版**够用；**建议不要用 snap/flatpak 装** —— 自动更新 + 沙箱在长期常驻的场景里不好控。
- **官方 CLI**（较新版本自带 `obsidian search/create/read…`）是操作 vault 最"官方"的接口，但**必须连一个正在运行的 Obsidian 进程**（IPC），命令面也窄。纯无头环境可用 `Xvfb + systemd user service` 常驻 GUI 版（注意 GPU 崩溃循环、SingletonLock 残留这类坑）。
- **headless 版只做 Sync/Publish（要订阅），不能读写本地 vault** —— 别指望它。

### 让 Agent 能用 vault 的三条路线（按推荐度）

| 路线 | 说明 | 取舍 |
|---|---|---|
| **① 直接读写文件**（推荐） | Agent 用文件读写/搜索工具操作 vault 里的 md | **最快最稳**，不依赖 GUI/进程，纯无头也能用 |
| ② 官方 CLI | `obsidian search …` | 依赖 Obsidian 进程活着；命令面窄 |
| ③ GUI 自动化 | xdotool 之类点界面 | 只在配置 Obsidian 本身时才需要 |

### B 类 · 自建 PHR（FHIR 官方标准那一条路，本模板没走）

`fastenhealth/fasten-onprem`（★2794，Go）、`jwilleke/yourphr`（社区续作）、`cfu288/mere-medical`（★307）、`Daniel-97/kura`、`FloorLamp/allos`（家庭/照护者向）。
**共同点**：把医院的 FHIR 数据拉进自建库自己看。**好处**是标准化、能做多源聚合；**代价**是要跑服务、要对接医院门户，且国内可达性差 → 不适合个人自用。

### C 类 · 用药追踪 web app

`damacus/med-tracker`、`stonecharioteer/sushruta`、`juscghwe/pilltracker`、`craigk5n/homecare` 等。
**共同点：都停在"提醒 + 依从性 + 存量"，没有一个做到"跟 AI 对话式管理病历"** → 所以这条路对个人自用没吸引力（也不做打卡）。

### D 类 · 技能站上可现成装的技能（技能市场）

| 技能 | 要点 |
|---|---|
| 官方的 Obsidian CLI 技能 | 官方 CLI 命令面的完整说明 |
| 通用健康顾问类技能（如 `health`） | **重点是安全边界**（绝不做诊断/治疗/开药）——与本项目边界一致 |
| 健康数据同步类技能（如 Apple Health 同步） | 把手机健康数据同步给 Agent |
| 病历管理/用药类技能（`medication-commander`、`medical`…） | **本地优先的病历管理 + 严格隐私边界**，含"绝不做"清单 |

> 有些技能站的检索页面是纯前端渲染、API 未暴露 → 想查得用浏览器渲染。

### E 类 · 医疗 MCP server（接口层）

清单仓库：`sunanhe/awesome-medical-mcp-servers`、`JuneYaooo/awesome-medical-ai-skills`（**带国内版 `-cn`**：按国内网络可达性/中文/NMPA 分类）。
FHIR：`the-momentum/fhir-mcp-server`。知识类：`andybrandt/mcp-simple-pubmed`、`JamesANZ/medical-mcp`。
**结论**：MCP 这条线全是"查外部医学知识 / 接医院 FHIR 库"，**没有一个是"管你自己 vault 里的病历"**。

### F 类 · 多 Agent + RAG 路线

`laoyubayunzi/crewAIWithRag`、`imcfyulong/Cymate-CrewAIWithRag`：把病历做成**向量库 + RAG**，多个 Agent 协作出报告。
**代价**：要维护向量库、可读性差；**收益**：问答检索强 → **将来 vault 变大后可作为增强手段**（Obsidian 侧也有把 vault 索引进 LanceDB 的工具）。

> 检索"病历管理 AI"时命中的大量 **Java SpringBoot 医院挂号/病案管理系统**（毕业设计型）不是一回事，**不要参考**。

## 三、模式归纳

1. **主流做法 = 纯 Markdown vault + Prompt/Skill**，不是写程序 —— 拍照/口述 → AI 按模板写笔记。零代码、可迁移、数据是自己的。
2. **"AI 管档案"和"AI 给建议"是两条线**：前者（本项目的定位）已经成熟；后者风险大，成熟项目普遍**主动设边界**（绝不做诊断/用药建议）。
3. **打卡类功能普遍是死路**：追踪型项目都停在提醒/依从性，用户懒得录 → 本项目明确不做打卡。
4. **可迁移性 = 最大卖点**：数据是普通 Markdown，换 Agent、换机器都不影响。

## 四、本模板最终怎么做（与上面各家的差异）

| 维度 | 选择 | 对比 |
|---|---|---|
| 载体 | Obsidian vault（纯 Markdown + 本地 git） | 同主流；不走向量库/FHIR |
| Agent 接口 | **直接读写文件** | 比依赖官方 CLI/进程更稳 |
| 组织 | **库 → 人 → 档案**，编号 1–9 顺号 | 比同类项目更强调多成员与阅读顺序 |
| 主线 | 感受 / 事件 / 药物 / **数值 CSV** / 体态 | 多数项目只有"报告 + 提醒"，没有跨年数值趋势 |
| 打卡 | **完全不做** | 与主流追踪类项目相反 |
| 输出 | **面向医生的脱敏 PDF 报告** | 同类少见（多数只做归档不做输出） |
| 药品 | 本机说明书库（SQLite + 精确匹配，**不上云**） | 同类多靠 AI 常识或外部 API |
| 边界 | 不诊断 / 不给用药建议 / 不判断紧急度 | 与各家"绝不做"清单一致 |

> 相关的"为什么这么设计"见 `设计说明.md`；归档流程见 `health-vault` 技能。
