# 设计说明 —— 为什么这么定

> **规矩在 `AGENTS.md`，这份文档解释"为什么"。**
> 规矩是"怎么做"，本文是"为什么这么做" —— 以后想改结构前先读一遍，避免把当初的考量推翻。

## 0. 设计目标与不做什么

**目标**：把散落的体检报告、化验单、处方、主观感受，变成一套**可检索、可追溯、可带走**的档案；让 AI Agent 当归档员，人只负责"扔单据 + 确认"。

**明确不做**（写进硬边界）：❌ 不诊断 ❌ 不给用药建议 ❌ 不判断紧急度 ❌ 不补造数据。
理由：一旦 Agent 开始"解释病情"，它的输出就会被当成医疗意见 —— 出错的代价由用户承担。**它只做搬运、结构化与检索**，判断留给医生。

## 1. 五条主线：为什么按"视角"切，而不按"科室/病种"切

| 主线 | 载体 | 回答 |
|---|---|---|
| 感受 | `3-不适记录` | 我什么时候有过什么不舒服？ |
| 事件 | `4-就医记录` + `2-检查报告` | 什么时候看了什么病、结果如何、用了什么药 |
| 药物 | `6-用药` | 这个药吃了多久、调过几次、为什么停 |
| 数值 | `5-指标` | 某个指标这几年的走势 |
| 体态 | `8-体重管理` | 我的体重 / 体成分是怎么变的？ |

**为什么不按科室（心内/消化/内分泌）或病种分？**
因为同一个数据会被多个科室用到（一次血常规同时服务内分泌和消化），按科室分必然重复。
而"视角"是**正交**的：一件事（就医）必然产生事件、可能产生数值、可能产生用药 —— 每条主线各自完整，不互相打架。

**为什么"指标"要单独成 CSV，而不是散在报告页里？**
报告是"事件快照"，指标是"时间序列"。做趋势（肝功这三年）必须跨事件聚合，散在各页就得全文搜索。CSV 让"某指标近 N 次"变成一次分组查询。

**为什么"体重管理"再单独一个类目，而不并进 `5-指标`？**

- **口径不同**：`5-指标` 装的是**有检验报告**的临床数值（有单位、有参考范围、有异常判定）；体脂秤是**自己测的**，App 只给"标准 / 偏高 / 偏低"标签、没有参考范围 —— 混在一起，"异常"这一列会失去意义。
- **频率不同**：临床数值一年几次，体脂秤可能一天几次。混表后"近 N 次血常规"这类按指标名分组的结果会被高频体重行淹没。
- **用途不同**：`5-指标` 面向医生（给医生的报告从它派生）；`8-体重管理` 面向自己（看曲线）。
- **代价（已知）**：想看"体重 + 肝功"这种跨表曲线，得合并两个文件 —— 真需要时写个脚本即可，不值得为它把两张表的口径揉在一起。

## 2. 目录编号 1–9 与"库 → 人 → 档案"

- **库 → 人 → 档案**：打开库先看到成员名字，点进去才是个人档案。**理由**：健康档案天生是"多人"场景（自己 + 家人），成员层在一开始就留好，比事后迁移便宜得多。
- **编号 1–8 = 阅读顺序**（基本信息 → 检查报告 → 不适记录 → 就医记录 → 指标 → 用药 → 视图 → **体重管理**），**8-知识库 / 9-模板 = 库级共享**。
  **理由 1**：数字前缀保证排序稳定（不像拼音/字母序会随新增内容漂移）。
  **理由 2**：共享内容（受控词表、模板）**只有一份**，加成员时不复制 —— 复制就会分叉，改词表要改 N 处。
  **理由 3**：早期用过 `00-/10-/15-/20-/30-/40-/50-/90-` 这种跳号（间隔式），但实际并不需要"中间插新目录"，反而看着怪 → 改成顺号，**不重排、不跳号**。
  **注意（同号不同层）**：成员目录里的 `8-体重管理/`（成员级）与库根的 `8-知识库/`（库级共享）**同号但不同层** —— 两个"8"不冲突，引用时带路径、别混。

## 3. 为什么"一次检查活动 = 一个目录"，而且汇总页与单报告页并存

```
2-检查报告/2026-09-11-协和体检/
├── 2026-09-11-协和体检.md   ← 汇总页（人读）
├── 报告/血常规-2026-09-11.md ← 单报告页（机器聚合）
└── attachments/             ← 原图
```

- **一个活动一个目录**：一次体检会产生 10+ 张单子，还必须把原图和报告放一起 —— 目录是唯一能"打包带走"的单位（直接 zip 给医生/换电脑）。
- **汇总页**：给人回看的入口（"这次都查了啥、有没有异常"）。
- **单报告页**：给检索聚合用（"近 10 次血常规"）。**更关键的是：心电图、CT、超声、内镜这类图像型/描述型报告进不了数值表**，单报告页是它们**唯一的文字载体**。
- **两者不重复**：汇总页是"合并视图"，单报告页是"拆分视图"，同一份数据的两种投影，只多占几 KB。

### 同一批近距离检查（≤7 天）为什么归一个活动

- 一周内的几张单子通常就是**同一次看病开出去的检查**（当天抽血、隔天做超声、几天后取报告），它们回答的是同一个问题——"这次看病查出了什么"。合并后仍是**一次接触 = 一行 + 一个目录**，回看时不用在目录之间拼图。
- **活动日期取"最早那天"**：活动是这件事的**起点**；取最早才能让目录按时间自然排序、并与就医记录那一行对齐（两边同名互链）。
- **各单据自己的日期不改写**：单报告页 `日期` / 原图文件名 / 指标行照抄各自单据 —— 只有"活动"是合并视图；单据日期一旦统一改写，"近 N 次血常规"的时间线就失真了。
- **≥8 天默认不合并**：跨度到一两周以上更像复诊或独立事件；硬合并会把"什么时候才查出来"这条线抹平。要合并仍可问用户，但必须由用户确认。
- **为什么必须问、不能自动判断**：7 天只是"可能同一次"的信号，不是证据；同一天的两张单子也可能是两家医院的两件事。判错的代价是**两个独立的就医事件被并成一个**——而就医记录只增不改，事后拆开要动已提交的历史。

## 4. 原图命名规范化（`YYYY-MM-DD_<项目>_原图[_pN].ext`）

**理由**：Markdown 里存不了"结构化元数据"，但**文件名可以**。一旦命名固定，就能用一条命令取全"近 10 次心电图原图"：

```bash
find 2-检查报告 -path "*attachments*" -name "*心电图*" | sort | tail -10
```

否则每次导出都要靠 Agent 一页页翻记录。**代价是归档时必须 rename**，但收益是永久可批量。多页扫描件用 `_p1/_p2` 后缀。

**一张单据含多个检查项目时**，项目名用 `+` 连接（`2024-12-02_电解质+肾功_原图.jpg`）—— 一张单子只拍一次，命名里带上全部项目名，任一项目名（`-name "*肾功*"`）都能捞到同一张原图；各报告页共用这张原图。

## 5. 受控词表（`8-知识库/项目名规范.md`）为什么是"地基"

如果同一个检查写成"心电图 / ECG / 心电检查"，**未来任何自动统计都会漏**（分组时被当成三项）。
所以：项目名只能取自词表；遇到新项目 **先问用户 → 定标准名 → 补进词表（连同别名）**。
**"错一个字就是另一个项目"** —— 这是唯一必须人工确认、不能靠模型猜的地方。

## 6. 为什么用 `ID` 列做配对

Markdown **表格的行挂不了块 ID**（`^id` 只能挂在段落/列表项上），所以"从检查活动页跳回就医记录那一行"没法用 `[[#^id]]`。
于是用 `ID` 列（`YYYYMMDD+序号`）+ 检查活动页 frontmatter 的 `就医ID` 双向配对，Agent 还能用它对账"有没有漏链"。

## 7. 只增不改 + 派生视图例外 + git

- **只增不改**：就医记录加行、指标加行、用药加条目、不适记录加行 —— **历史行永不动**。要订正就**追加 + 标注**。
  **理由**：这些是医疗记录，篡改历史比留个错字危险得多；而且下游（视图、报告）都建立在这些源数据上。
- **唯一例外**：`7-视图/` 三件套是**派生文件**（从上游重生成）。**理由**：视图是投影，必须随时反映最新上游；源数据不动，视图丢了也能再生成。
- **`1-基本信息/` 是基准线，默认只读**：除本人主动要求增 / 改 / 删，agent **不改、也不问"要不要同步最新数据"**。
  **理由**：数字与说法每次都有细微差别，每次都追问"改不改"是纯开销；本页是**本人自述的那一版基线**，后来的测量与报告各落各的位置（指标表 / 体重管理 / 报告页），要看对比就两边并排 —— **差异不是冲突，是不同时间的两次记录**。
- **每次归档都 commit**：本地 git 快照 = 后悔药 + 审计。**纯本地，无远程仓库** —— 病历不上云。

## 8. 为什么就医记录**同时**记用药（有意重复）

- 就医记录的「用药/治疗」列 = **这一次开了什么药**（事件快照）→ 反查某次就诊时**一眼看到，不用点链接**
- `6-用药/用药流水.md` = **这个药吃了多久、调过几次、为什么停**（药物一生）

**顾虑**：重复就是可能不一致。**取舍**：查一次就诊的频率远高于"核对一致性"，所以接受重复，并规定**两处都要写，只更新一处算待核对**。

## 9. 为什么"不适记录"只有四列，而且不做打卡

- **四列**（日期 / 不适的感受 / 我怎么处理的 / 持续多久）：它是**纯记录**，唯一用途是日后**溯源**"之前有没有过这种不适"。加"程度/诱因/状态"这些字段会让填写成本上升，而它最大的敌人是**人懒得写**。
- **照原话录**：用户说"胃有点堵得慌"，就记"胃有点堵得慌"，不替换成"上腹不适" —— 改写会丢掉他自己的描述精度。
- **不做打卡/依从性记录**：用户明确拒绝（"每天重复汇报很消耗精力且无聊"）。**一个没人愿意用的记录系统等于没有**。
- **与「自查」的区别**：自查 = 自己判断 + 自己吃药处理了，算**一次医疗接触**；不适记录 = 只是有不舒服。两者并存、不互相覆盖。

## 10. 药名用"通用名（剂型）"，药品库为什么要做成 SQLite

- **通用名（剂型）**：`布洛芬（缓释胶囊）`。商品名（芬必得）只作别名 —— 商品名会变、会重复，通用名才是药的身份。
- **不做向量检索，做精确匹配**：药名**错一个字就是另一个药**（`阿司匹林` vs `阿司匹林双嘧达莫`）。语义检索在这里是**风险**，不是优势。
- **做成 SQLite + 查询脚本**：一份完整中文说明书库上万条、每条数千字。塞进上下文既贵又慢 → **脚本查、只取命中行**（默认截断，需要原文再加 `--full`）。
- **许可**：公开可得的整理集多有版权问题 → **仅个人自用，不再分发**；模板仓库不附带任何药品数据，授权来源见 `用药指南/索引.md`。
- **不记频次（一天几次）**：用户回忆不准，记了只会产生 `[信息缺失]` 噪声。用药记录回答的是"吃过什么药、吃了多久、为什么停"，不是依从性台账 —— **只记药名（通用名＋剂型）+ 大概规格/剂量 + 时间线**。

## 11. 为什么"面向医生的报告"必须脱敏 + 出 PDF

- **脱敏**：报告是要**带出门、交给外人**的东西。只放 性别 / 年龄段 / 身高体重 / 过敏史 / 慢病 / 用药 / 指标；不放全名、身份证、电话、住址、单位。完整版留在库里。
- **PDF 不是 Markdown**：医生的使用场景是**打印、翻阅、存档**，不是在自己的编辑器里跑渲染。
- **四段结构**（本次不适 / 近期用药 / 相关化验指标 / 既往要点）：照着**门诊问诊的顺序**排 —— 陈述症状、交代用药、给出可对比的数据、补充背景。它替代不了医生，但能让 10 分钟的问诊省下 5 分钟。

## 12. 会话怎么用（投递窗口，不是分拣口）

往哪个会话扔单据都行 —— Agent 按单据类型**自动分发**到对应目录，所以用户不必纠结"放哪个会话"。
**带照片的会话要短**（图片每一轮都要重发，上下文涨得快、最容易触发压缩）；纯文字会话可以很长。
归档完成后删/归档会话都不影响库 —— **数据在磁盘文件里，不在会话里**（这是"数据与工具解耦"的直接好处）。

## 13. 已知取舍与未来可做

| 取舍 / 待办 | 说明 |
|---|---|
| 报告项目名仍需人工确认 | 受控词表是地基，宁可多问一句 |
| 原图归档依赖 rename 纪律 | 靠规律而非工具保证；出错时靠 git 回溯 |
| 7 天合并阈值仍需人工确认 | 阈值只是"问一句"的触发条件，不是自动合并规则；归属一律用户定 |
| 药品库无中文商品名批量源 | 商品名靠逐条确认；库只保证通用名 |
| 未做：多成员视图命名约定 | 单人时直接用 `主档案.md`；多人时用 `主档案-<成员>.md` |
| 未做：自动复查提醒 | `下次复查` 列已预留结构化日期，将来可接定时任务 |
| 未做：报告 PDF 的一键生成器 | 已定方案（HTML + 打印样式 → 无头浏览器打印），待首次出报告时落地 |

## 14. 边界（无论怎么改都不要破）

1. **不诊断、不给用药建议、不判断紧急度** —— 出现胸痛、呼吸困难、大出血、意识丧失、突发严重神经症状，**先让用户就医**，再谈归档。
2. **不补造数据** —— 缺失写 `[信息缺失]`，推断写 `[推断]` 并说明依据，数值拿不准写 `[待核对]` 并留空。
3. **保留不确定性**，不替医生把话说圆。
